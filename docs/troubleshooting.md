# Troubleshooting and hard-won details

Each point below cost at least one debugging session. Don't undo them casually.

## Radio

- **Set the XIAO's RF switch.** The XIAO ESP32-C6 routes its antenna through an RF switch:
  GPIO3 powers it (LOW), GPIO14 selects the antenna (LOW = internal, HIGH = U.FL socket).
  ESPHome does not set these pins. Left unset, the board heard the inverter at about −94 dBm,
  which is unusable. With them set it was about −66 dBm. `esp32c6.yaml` sets both.
  `external_antenna` in the secrets picks the socket.
- **Keep the BLE scan window small** (passive, 30 ms every 1280 ms). The ESP32-C6 has a single
  2.4 GHz radio path. A tracker that scans continuously next to Zigbee starves the login.
- **Status 15 or frequent link drops (reason 0x08).** Check whether radio coexistence is the
  cause: flash the BLE-only variant (`esp32c6-bleonly.yaml`, generated by
  `tools/make_bleonly_board.py`). If it holds the link where the full image does not, the
  problem is Zigbee/BLE coexistence. If it drops too, look at placement, antenna and distance.

## The inverter

- **One BLE central at a time.** The inverter serves a single connection. The S-Miles app, the
  ha-hiflow-ble integration or a BLE proxy competing for the slot looks exactly like a broken
  bridge. While the bridge is connected, the inverter barely advertises, so "the app cannot find
  the inverter" usually just means the bridge holds the slot. Unplug the board to free it.
- **The login timestamp must be close to the inverter's clock.** The inverter drops the link on
  a login whose time lags its own too far (55 s behind passed, 90 s did not). The board has no
  real time: after a power cut its clock restarts from the last value saved to flash. That is why
  the session adopts the inverter's time from the V0 pairing reply (field 2) before every login.
- **The session key rotates.** The inverter hands out its current `encRand` in the V0 pairing.
  The bridge pairs after every boot and after every failed handshake, and never stores the key.
- **An abrupt loss is not a lockout.** If the board loses power mid-session, it reconnects like
  any other peer, and data is back within about a minute.
- **Status 13:** the inverter wants the BLE PIN for this `ble_id` and none is configured, or it
  was refused. Set `hiflow_ble_pin` to the PIN from the S-Miles app. After one accepted PIN, the
  `ble_id` is whitelisted. Keep it.
- **One login per connection.** A second login into a live session kills the link without a
  word, the same way a stale key or a refused identity does.

## Protocol

- **Never decode the login acknowledgement with the request layout.** Its fields differ, and the
  decoded "time" is garbage. Only plausible values (2024–2040) are adopted.
- **`RealDataNew` fields 12/13 must not be declared.** The device sends field 13 as an embedded
  message while the reference `.proto` says `uint64`. Python protobuf skips it silently; nanopb
  aborts with `wrong wire type`, and then nothing decodes.

## Zigbee / Home Assistant

- **Open *Add device* before the board boots.** After a boot, ESPHome tries to join ten times,
  one second apart, then only every 10 minutes. A board flashed before pairing was opened sits
  there unjoined; reset it while *Add device* is open.
- **No BLE link and `BDB Device Reboot failed` after switching firmware: erase the flash.** The
  bridge's `nvs` and `zb_fct` partitions (`0x370000–0x3E1000`) overlap other images' data; the
  BLE proxy this was seen with keeps its `nvs` at `0x390000`. `esphome run` only writes the
  bootloader, the partition table and the app, so the bridge's partitions still hold the
  proxy's data. Seen after a proxy → bridge switch: the status stayed at 10 (no link came
  up), and after the next reset the log repeated `The BDB Device Reboot failed with
  status(0x03)` every second. `tools/flash_config.sh` erases the flash by itself when the
  partition table on the board differs; after an erase, open *Add device* again before the
  board boots. The same applies the other way round: flash the proxy with
  `tools/flash_config.sh /path/to/proxy.yaml` as well.
- **Boot loop right after "Device rebooted": update the coordinator.** With a ConBee III on
  deCONZ firmware 0x264d0900, every reboot of a joined bridge (end device or router, with or
  without BLE) crashed in esp-zigbee-lib 2.0.4 about 5 s after boot, and the board went round in
  a reset loop. The release library dies while printing the assert; built with
  `CONFIG_ZB_DEBUG_MODE: y` it reads
  `assert failed: nwk_fwd_handle_nwk_confirm nwk_forwarder.c:957`. On firmware 0x26550900 the
  same board rebooted cleanly every time. Flash the coordinator with dresden elektronik's
  GCFFlasher (`GCFFlasher -b 115200 -d /dev/ttyUSB0 -f deCONZ_ConBeeIII_0x26550900.bin.GCF`;
  without `-b 115200` it stops silently after "send uart reset") while Home Assistant is
  stopped. Other coordinators are untested.
- **`report: force`** on every sensor. Otherwise ZHA leaves analog-input entities `unknown`.
- **After changing the sensor list, re-interview in ZHA.** Every sensor is one endpoint, numbered
  in list order. ZHA binds entities by unique id and otherwise mixes old names with new values.
  Remove the device, let it re-join, then run `tools/ha_fix_bridge_entities.py`. Add new
  sensors before the status sensor, so the status keeps the last endpoint.
- **Energy dashboard:** ZHA analog inputs are always `measurement`. Use the template sensor from
  `docs/ha-energy-template.yaml`, which is `total_increasing` and ignores missing values.

## USB and logging

- **Run the deployed board at `WARN`.** A USB charger is not a USB host, so every log write on
  `USB_SERIAL_JTAG` can block. At `INFO` the board reset every ~5 minutes on a charger. At
  `VERBOSE` it ended in watchdog resets. Use `DEBUG` (handshake steps) and `VERBOSE` (GATT
  errors) only for short sessions on a computer's USB port. `tools/quicktest.sh` builds a DEBUG
  copy for that.
- **Opening the USB-Serial/JTAG port can hold the chip in reset.** With the default modem lines
  (DTR asserted) the board stops: no log lines, no BLE, and the values in HA freeze. Open it with
  `serial.Serial(); s.dtr = False; s.rts = False; s.open()`, as `tools/quicktest.sh` does.
  Closing the port can reset the board too. `esphome logs` is unreliable on this port.
- **After a physical re-plug the console often stays silent.** Run
  `esptool --after hard_reset flash_id` to re-initialise it.
- On Linux, `/dev/ttyACM0` needs a udev rule such as
  `SUBSYSTEM=="tty", ATTRS{idVendor}=="303a", MODE="0666"`, or membership in the serial group
  (`uucp` or `dialout`).
